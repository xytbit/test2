eBPF for the Curious Beginner

You can attach a tiny program to the kernel and observe it without writing a kernel module. Here is the honest first hour.

BY SABBIR RAHMAN · Systems study group

eBPF sounds intimidating, and it deserves to. But the first-hour version is small: a verifier that checks your program is safe, a just-in-time compiler, and the ability to attach that program to specific kernel events. You are not 'writing a kernel module' — you are attaching a sandboxed program to a hook.

The pieces

  • A program: bytecode written in C and compiled to BPF.
  • A verifier: proves the program terminates, bounds-checks its memory, and touches nothing dangerous.
  • A JIT: compiles the bytecode to native instructions on load.
  • A hook: syscalls, tracepoints, kprobes, or network packets.
  • Maps: the only way your program talks to userspace.
// count every execve
extern int bpf_trace_printk(const char *fmt, ...);

SEC("tracepoint/syscalls/sys_enter_execve")
int count(void *ctx) {
  bpf_trace_printk("someone ran a command\n");
  return 0;
}

That program compiles, passes the verifier, and prints a line for every execve on the whole system. No module, no reboot. It is the same mechanism that powers modern observability tools — you are not reading about the machinery, you are running it.

What the verifier actually checks

The verifier is the reason eBPF is safe enough to ship in production kernels. It simulates your program's paths and proves three things: no unbounded loops, no out-of-bounds memory, and no dangerous pointer arithmetic. Your program is not trusted; it is checked.

The kernel does not trust your program. The verifier proves it is safe, and the JIT makes it fast. That trade — safety for speed — is the whole design.

For the club, eBPF is the cleanest doorway into 'I can observe the kernel' — no modules, no panics, just a small program and honest curiosity. The reading group's notes include the toolchain setup we use on the club lab machines.
