Reading the Linux Kernel Without Panicking

Thirty million lines is not a book to read — it is a map to navigate. A practical method that works for students.

BY MEHERUN NESA · Networking study group lead

The Linux kernel is the largest codebase most students will ever touch, and the worst possible way to approach it is to 'read it'. Nobody does. What actually works is navigating it like a map: pick a path, follow the types, and ignore everything else.

Pick one entry point

Choose a single syscall or subsystem — say, the read() path, or the TCP receive path. Everything else in the kernel is background noise you are allowed to ignore until it becomes relevant. Depth beats breadth.

read() → do_syscall_64() → ksys_read()
  → vfs_read() → the file's read callback
  → eventually a device or socket layer

Follow the function call tree, not the whole source.

Follow the types, not the code

Kernel code is dense because it is type-driven. When you meet an unfamiliar structure — say, struct file or struct sk_buff — stop and read its definition and its comments. Most of the design lives in the type definitions, not in the bodies of functions.

  • Start from the syscall, follow the call chain.
  • Read struct definitions before function bodies.
  • Use the navigation tools: grep, ctags, and the online elixir browser.
  • Write a one-paragraph note after each session; it forces understanding.
  • Do not try to understand locking on the first pass.

A session should end with a single paragraph you could explain to a classmate. If you cannot write it, you were scrolling, not reading. The goal is not coverage — it is one path understood end to end.

NOTE — We run this as a four-week track in the Systems group using a single driver as the running example.
