What Actually Happens When You Press Enter

A keystroke becomes a process. The journey through the kernel is short, and worth knowing exactly once.

BY ARIF CHOWDHURY · Systems study group lead

Every command you run begins as a physical event: a key goes down, a voltage changes on a wire, and a signal travels from the controller to your CPU. But between that keystroke and the shell printing a prompt again, a surprisingly small number of precise things happen. This is the journey, roughly, of pressing Enter in a terminal.

1. The interrupt

The keyboard controller raises an interrupt. The CPU stops whatever it was doing, looks up the interrupt vector table, and jumps to the driver's handler. None of this is magic — it is just a table of function pointers, and the hardware knows how to find it.

hardware interrupt → IRQ line → driver handler
  → scancode read from the controller
  → scancode translated to a keycode
  → keycode queued for userspace

2. The pipe to userspace

The kernel does not hand the terminal program raw keycodes. It writes a byte to a pseudo-terminal. The terminal emulator reads that byte, applies its own keymap, and appends it to its line buffer. When you press Enter, the emulator sends the whole line as a read on the pty's master side — and the shell, which has been blocked in a read() on the slave side, finally returns.

3. Parse, look up, fork

The shell parses the line, expands variables, and looks up the executable in PATH. Then it forks. The new child — a copy of the shell — calls execve, which replaces its memory image with the target binary. One of the parent's jobs is to wait: it blocks in waitpid until the child exits, then prints a prompt.

read() on the pty slave
→ shell parses + expands
→ fork() → execve()
→ child runs, parent blocks in waitpid()
→ exit status → next prompt

Why this matters

None of these steps are required by any specification — they are the accumulated result of decisions made over forty years. But knowing the shape of the pipeline means that when something breaks, you do not guess. You ask which layer the break is in: hardware, driver, terminal, shell, or the process itself. The skill of debugging is mostly the skill of knowing which layer to suspect.

Debugging is the process of correctly shrinking the search space. Everything else is typing.
