The Anatomy of a URL

Every byte in the address bar has a job. A short tour of the parts nobody reads, because we are all too busy.

BY SADIA AKTER · Web study group lead

The address bar is the most-translated string on your machine, and almost nobody can parse it by eye. So let's do it once, properly, because a URL is just a specification for where to find a resource and how to ask for it.

https://user:pass@example.com:443/path/to/page?q=value#frag
└─scheme┘ └──userinfo──┘ └──host────┘ └port┘ └──path─────┘ └query─┘ └frag┘
  • Scheme: the protocol — how to speak. https means 'encrypted HTTP'.
  • Userinfo: credentials embedded in the URL. A bad idea; the RFC deprecates it.
  • Host: the name the DNS system resolves to an IP address.
  • Port: which service on that host. Omitted when it is the default.
  • Path: which resource on that server. The server, not the URL, decides what it means.
  • Query: structured parameters, sent to the server. This is not a secret channel.
  • Fragment: a location inside the page. Never sent to the server — the browser keeps it.

What the browser does with it

The browser splits the URL, resolves the host through DNS (with caching at every layer), opens a TLS connection to the resolved IP and port, sends a request line built from the path and query, and then — and only then — does the server decide what to return. Every part of the URL had a job in that sequence, and none of them are decorative.

GET /path/to/page?q=value HTTP/1.1
Host: example.com
Accept: text/html

The web's apparent magic dissolves the moment you can trace one request end to end. It is the same discipline as the keystroke post: know which layer you are in, and the system stops being a black box.
